Concept 01

Distributed training: sharding the model state

With mixed-precision Adam, every parameter costs about 16 bytes of training state: 2 for the weights, 2 for the gradients, and 12 for the fp32 master copy and two optimiser moments. A 7B model needs roughly 112 GB before any activations, more than one GPU holds.

  • DDP (data parallel): every GPU keeps a full copy and sees different data. Gradients are averaged with an all-reduce.
  • ZeRO / FSDP: shard the state across GPUs so each keeps only a slice, and gather it just in time. ZeRO-1 shards optimiser states, ZeRO-2 adds gradients, ZeRO-3 (FSDP) adds the weights.
  • Tensor parallel: split each large matrix across GPUs. It needs fast links, so it is used inside one node.
  • Pipeline parallel: put different layers on different GPUs (next section).
per-GPU bytes: DDP = 16P ZeRO-1 = 4P + 12P/n ZeRO-2 = 2P + 14P/n ZeRO-3 = 16P/n

# Option B: FSDP (shard each transformer block's parameters, gradients and optimiser state)

Scaling notes

  • Measure MFU (model FLOPs utilisation): useful FLOPs per second divided by peak. 35–55% is good on large LLM runs. Low MFU usually means data loading, small batches or slow communication.
  • Checkpoint often and make resuming exact (optimiser state, data position, random state). Large runs hit hardware failures.
  • Combine methods: for example FSDP across nodes and tensor parallel inside each node.
Concept 02

Pipeline parallelism and the bubble

In pipeline parallelism, stage s holds a block of layers. A batch is cut into micro-batches that flow through the stages. At the start and end some stages sit idle: the bubble.

bubble fraction = (S − 1) / (M + S − 1) S = stages, M = micro-batches

More micro-batches shrink the bubble. Schedules such as 1F1B and interleaved pipelines also cut activation memory.

Concept 03

Serving LLMs: batching and the KV cache

Generating text is memory-bandwidth bound: each new token reads all the weights. The fix is to serve many requests at once. Naive static batching waits for the longest request in a batch. Continuous batching (used by vLLM, TensorRT-LLM, SGLang and others) lets a new request take a slot the moment another finishes.

Concept 04

Experiment tracking and hyperparameter search

Every serious team tracks experiments: the code version, data version, settings, metrics over time and output files. Without it, nobody can reproduce a result. Common tools are MLflow and Weights & Biases.

For tuning, the standard tools are Optuna and Ray Tune. They use random or Bayesian search and early stopping of bad trials. Random search beats a grid when only a few settings matter, because a grid wastes trials repeating the same value of the important setting.

Python · MLflow tracking and an Optuna study
import mlflow, optuna

def objective(trial):
    lr = trial.suggest_float("lr", 1e-5, 1e-2, log=True)
    wd = trial.suggest_float("weight_decay", 1e-4, 1e-1, log=True)
    with mlflow.start_run(nested=True):
        mlflow.log_params({"lr": lr, "weight_decay": wd})
        model = build_model()
        for epoch in range(20):
            val = train_one_epoch(model, lr, wd)
            mlflow.log_metric("val_loss", val, step=epoch)
            trial.report(val, epoch)
            if trial.should_prune():                    # stop clearly bad trials early
                raise optuna.TrialPruned()
    return val

mlflow.set_experiment("churn-model")
with mlflow.start_run():
    study = optuna.create_study(direction="minimize", pruner=optuna.pruners.MedianPruner())
    study.optimize(objective, n_trials=50)
    mlflow.log_params(study.best_params)

What to log

  • Git commit, dataset version or hash, full config, random seeds, library versions.
  • Training and validation metrics per step, plus final test metrics, kept separate from tuning metrics.
  • The model file and a small set of example predictions you can eyeball.
Concept 05

Monitoring and drift

A deployed model degrades silently because the world changes. Data drift is a change in input distribution. Concept drift is a change in the relationship between inputs and the right answer. Labels often arrive late, so teams watch input and output distributions first. Two common measures:

PSI = Σ over bins (actualᵢ − expectedᵢ) · ln( actualᵢ / expectedᵢ ) < 0.1 stable · 0.1–0.25 watch · > 0.25 act KS = max over x of | F_live(x) − F_ref(x) |

Python · PSI and a KS test
import numpy as np
from scipy.stats import ks_2samp

def psi(ref, live, bins=10, eps=1e-6):
    edges = np.quantile(ref, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(ref,  edges)[0] / len(ref)  + eps
    a = np.histogram(live, edges)[0] / len(live) + eps
    return float(np.sum((a - e) * np.log(a / e)))

stat, p = ks_2samp(ref_feature, live_feature)
if psi(ref_feature, live_feature) > 0.25:
    alert("feature drifted: investigate the pipeline, then consider retraining")

Monitoring in practice

  • Watch inputs, predictions and (when they arrive) outcomes. Also watch data quality: missing rates, ranges and new categories.
  • Training-serving skew, where a feature is computed differently online than offline, causes more production bugs than model choice. Reuse the same code or a feature store.
  • Define in advance what triggers retraining, rollback or a human review.
Concept 06

A/B testing a model

Offline metrics do not guarantee business results. Industry practice is to compare models on live traffic with a randomised split. Before starting, decide the metric, the smallest effect that matters, and the sample size.

z = (p_B − p_A) / √( p̄(1−p̄)(2/n) ) n per arm ≈ 2 · (z_α/2 + z_power)² · p̄(1−p̄) / δ²

Python · a two-proportion test and sample size
from statsmodels.stats.proportion import proportions_ztest
from statsmodels.stats.power import NormalIndPower
from statsmodels.stats.proportion import proportion_effectsize

z, p = proportions_ztest(count=[conv_a, conv_b], nobs=[n_a, n_b])
es = proportion_effectsize(0.055, 0.05)                    # target rate versus baseline
n = NormalIndPower().solve_power(es, power=0.8, alpha=0.05)
print(f"need about {int(n)} users per arm")

Common traps

Peeking at results every day and stopping when p < 0.05 inflates false positives. Fix the sample size in advance, or use a sequential test designed for repeated looks.

model.eval()

onnx_out = sess.run(None, {"x": x})[0]

assert np.allclose(onnx_out, torch_out, atol=1e-4)      # always compare exported and original on the same inputs

Rollout

  • Shadow: the new model runs on real traffic but its answers are not shown. Compare with the current model.
  • Canary: send 1–5% of users to it, watch metrics, then ramp up.
  • Keep the previous version one switch away. Test rollback before you need it.
Concept 08

Small details that matter

All-reduce

Operation that sums a tensor across all GPUs and gives everyone the result. Ring all-reduce keeps per-GPU traffic nearly constant as GPUs grow.

bytes per GPU ≈ 2 · (n−1)/n · size
dist.all_reduce(grad)

Gradient accumulation across ranks

Skip the all-reduce on intermediate micro-steps and sync only on the last one.

sync every k steps
with model.no_sync(): loss.backward()

MFU

Share of the hardware's peak FLOPs that your training actually uses.

MFU = 6·P·tokens_per_s / peak_FLOPs
mfu = 6 * n_params * tok_s / peak

Activation checkpointing

Recompute activations during backward instead of storing them. Pairs with sharding to fit bigger models.

compute +30%, memory ↓↓
torch.utils.checkpoint.checkpoint(block, x)

Prefix caching

Reuse the KV cache of a shared prompt start, such as a long system prompt, across requests.

TTFT ↓ for repeated prefixes
--enable-prefix-caching

Speculative decoding

A small model drafts several tokens and the large model verifies them in one pass. Output is unchanged, latency drops.

speedup ≈ accepted tokens per step
LLM(model, speculative_config={...})

Chunked prefill

Split long prompt processing into pieces mixed with decode steps so short requests are not blocked.

smoother TPOT
--enable-chunked-prefill

Training-serving skew

A feature computed differently in training and in production. It silently harms accuracy.

offline feature ≠ online feature
assert np.allclose(offline, online)

Data and concept drift

Inputs changed versus the relationship to labels changed. Different fixes: reweight and monitor versus retrain.

P(x) changes vs P(y|x) changes
monitor(psi, label_delay)

Model registry

A central store of model versions with metadata, metrics and promotion stages.

staging → production
mlflow.register_model(uri, "churn")

Reproducibility

Fix seeds, record versions, and know that some GPU kernels are nondeterministic.

same code + data + seed ≈ same result
torch.use_deterministic_algorithms(True)

Checkpoint and resume

Save model, optimiser, scheduler, data position and random state so a crashed run continues exactly.

state = {model, opt, sched, step, rng}
torch.save(state, path)
